# 단계: 검증

기능: $FEATURE

## 출력 (이 파일 하나만 쓴다)
$WORK/VERIFY.md

## 산출물 외에 수정해도 되는 것
- `$ROOT/src/**/*.test.ts` — 테스트 파일 (신규 작성·기존 수정)

## 입력 (읽기만, 절대 수정 금지)
- `$WORK/DESIGN.md` — "검증 기준" 섹션이 테스트의 근거다
- `$WORK/IMPL.md` — 실제 구현 내용
- `$WORK/JUDGE.md` — 설계 주장 감사 결과

## 이 저장소의 테스트 환경

vitest 4. `npm test` = `vitest run`.

- 테스트 파일 위치: 대상 소스 **옆**에 `*.test.ts` (예: `src/lib/format.test.ts`)
- 수집 대상: `src/**/*.test.ts` 만 (`vitest.config.mts`)
- 환경: **node**. jsdom 이 없으므로 **React 컴포넌트 렌더 테스트는 쓸 수 없다.**
  컴포넌트 동작 검증이 필요하면 로직을 순수 함수로 뽑아 그걸 테스트하거나,
  "사람이 확인할 것"으로 넘긴다
- `@/` 별칭은 `src/` 를 가리킨다. 상대 경로 대신 이걸 쓴다
- 전역 API 없음. `import { describe, it, expect, vi } from 'vitest'` 로 명시 import
- 참고 예시: `src/lib/format.test.ts`

**돌릴 수 없는 것** — `.env` 는 gitignore 대상이라 없을 수 있고, 있어도 더미 값이다.
DB·S3·디스코드에 실제로 붙는 테스트는 쓰지 마라. 외부 호출은 `vi.mock` 으로 막는다.
`src/lib/env.ts` 를 import 하는 모듈은 `.env` 없이 throw 하므로 그 경로도 mock 대상이다.

## 할 일

1. DESIGN.md 의 검증 기준을 `src/**/*.test.ts` 로 옮긴다. 기준 하나당 케이스가
   최소 하나씩 대응돼야 한다.
2. **불변식 회귀 테스트.** 이번 변경이 아래를 깨뜨릴 수 있는 자리에 있으면 그걸
   고정하는 케이스를 넣는다. 해당 없으면 "해당 없음"이라고 쓴다.
   - "최신 버전"은 `versionNo desc` 정렬로 구한다 (컬럼이 아니다)
   - 1문서 = 1파일
   - 파일이 앱 서버를 거치지 않는다 (presigned PUT/GET)
   - 접근 제어는 디스코드 길드 멤버십 하나 (역할·권한 개념 없음)
3. **테스트로 못 덮는 것을 사람 체크리스트로 넘긴다.** "어느 화면에서 무엇을 하면
   무엇이 보여야 하는가" 수준의 재현 절차로 쓴다.

## VERIFY.md 필수 섹션
- STATUS 라인 (첫 줄)
- 작성한 테스트 파일과 케이스 목록
- 검증 기준 ↔ 테스트 케이스 대응표 (빠진 기준이 있으면 명시)
- 불변식 회귀 테스트 결과 (위 4개 각각: 넣음 / 해당 없음)
- 테스트로 덮지 못한 부분 + 사람이 확인할 것 체크리스트 (재현 절차)

## 중요
테스트 통과 여부는 이 세션이 판정하지 않는다. 파이프라인 셸이 `$TEST_CMD` 를 별도로
실행해서 판정한다. "통과할 것으로 보인다" 같은 문장을 쓰지 마라.

## 금지
- **소스 코드를 수정하지 않는다.** 고칠 수 있는 것은 `*.test.ts` 뿐이다.
  구현이 틀렸으면 테스트를 느슨하게 만들지 말고 STATUS: BLOCKED
- 패키지를 추가하지 않는다 (jsdom·@testing-library 포함). 필요하면 STATUS: BLOCKED
- `vitest.config.mts` 와 `package.json` 을 수정하지 않는다
- `it.skip` / `it.todo` / 항상 참인 단언으로 개수만 채우지 않는다
